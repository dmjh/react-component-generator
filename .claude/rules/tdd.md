# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 "이번만 예외"를 만들지 않는다.

## 1. 적용 기준

### TDD를 반드시 적용하는 대상

- **비즈니스 로직**: 도메인 규칙, 계산, 상태 전이, 데이터 변환
- **API**: 라우트 핸들러, 요청 검증, 에러 매핑, 외부 API 호출 래퍼
- **유틸 함수**: 순수 함수, 파서, 포매터, 정규화 로직
- **버그 수정**: 버그를 재현하는 실패 테스트를 먼저 작성한 뒤 고친다

### TDD가 불필요한 대상

- **타입 정의**: `interface`, `type` 선언만 있는 파일
- **설정 파일**: `tsconfig`, `vite.config`, `eslint.config`, `package.json` 등
- **순수 UI**: 로직 없는 마크업/스타일 컴포넌트, CSS
- **SQL**: 스키마, 마이그레이션, 단순 쿼리

판단이 애매하면 **로직이 있으면 적용**한다.

## 2. RED-GREEN-REFACTOR 사이클

### RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- 테스트를 **반드시 실행해서 실패를 확인**한다. 실행하지 않은 RED는 RED가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 오타, import 오류, 문법 오류, 잘못된 셋업으로 인한 실패는 RED로 인정하지 않는다. 테스트를 고쳐서 올바른 이유로 실패시킨다.

### GREEN: 테스트를 통과시키는 최소 코드

- 테스트를 통과시키는 **최소한의 코드만** 작성한다. **YAGNI**: 아직 테스트가 요구하지 않는 기능, 분기, 옵션을 넣지 않는다.
- **신규 테스트와 기존 테스트 모두 통과**하는지 전체 스위트를 실행해 확인한다.

### REFACTOR: 구조 개선

- 중복 제거, 이름 개선, 헬퍼 추출만 수행한다.
- 리팩터링 중 **항상 green을 유지**한다. 변경마다 테스트를 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 다음 RED로 간다.

### 반복

다음 동작에 대한 **RED로 돌아간다.** 요구된 동작이 모두 테스트로 덮일 때까지 반복한다.

## 3. 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 그 코드를 삭제하고 RED부터 재시작**한다.
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 임시 파일, 별도 브랜치 보관, 복사해 두고 보면서 다시 쓰기 모두 포함한다.
- 삭제한 코드는 테스트 주도로 처음부터 다시 작성한다.

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드는 테스트도 단순하다. 비용이 거의 없는데 회귀 방지 효과는 그대로다. 단순해 보이는 코드가 가장 자주 조용히 깨진다. |
| "나중에 테스트 추가하겠다" | 나중에 쓴 테스트는 구현을 따라 쓴 확인용이라 설계를 이끌지 못하고 결함을 못 잡는다. 실제로 "나중"은 오지 않는다. |
| "시간이 없다" | 테스트 없는 코드는 디버깅과 재작업으로 더 많은 시간을 쓴다. 급할수록 RED-GREEN의 짧은 루프가 빠르다. |
| "삭제하면 낭비" | 이미 쓴 시간은 매몰 비용이다. 검증되지 않은 코드를 유지하는 비용이 더 크다. 테스트 주도로 다시 쓰면 보통 더 작고 정확하다. |
| "프로토타입이다" | 프로토타입은 프로덕션이 된다. 버릴 코드라면 테스트도 필요 없지만, 남길 코드라면 처음부터 TDD로 쓴다. 로직이 있으면 적용 대상이다. |

## 5. 프로젝트별 규칙 우선

- 프로젝트의 **`CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 그것이 우선**한다. 충돌하는 부분은 프로젝트 규칙을 따른다.
- **이 파일은 기본값(fallback)** 이다. 프로젝트 규칙이 없거나 침묵하는 부분에만 적용된다.

# commit: 변경사항 분석 후 컨벤션 커밋

## 원칙

- 사용자 승인을 기다리지 않는다. 분석과 분류가 끝나면 바로 커밋한다.
- `git push`는 하지 않는다. 사용자가 따로 요청할 때만 한다.
- `--no-verify`, `--amend`, `git reset --hard` 등 훅 우회·이력 변경 명령은 사용자가 명시적으로 요청하지 않으면 쓰지 않는다.
- `.env`, 키·토큰, 인증서 등 비밀 정보로 보이는 파일은 커밋 대상에서 제외하고 사용자에게 알린다.

## 절차

### 1. 변경사항 분석

```bash
git status --short
git diff            # 스테이징되지 않은 변경
git diff --staged   # 이미 스테이징된 변경
git log --oneline -10   # 기존 메시지 스타일 참고
```

- 새로 추가된 파일(untracked)도 내용을 읽어 변경 의도를 파악한다.
- 변경이 없으면 "커밋할 변경사항이 없습니다"라고 알리고 종료한다.
- Git 저장소가 아니면 그 사실을 알리고 종료한다.

### 2. 논리적 단위로 분류

- 하나의 커밋은 하나의 목적만 담는다. 서로 다른 목적의 변경은 나눈다.
  - 예: 기능 추가 + 무관한 리팩터링 + 설정 변경 → 커밋 3개
- 함께 바뀌어야 의미가 있는 파일은 한 커밋으로 묶는다. (구현과 해당 테스트, 컴포넌트와 스타일 등)
- 한 파일 안에 서로 다른 목적의 변경이 섞여 있으면 사용자에게 알리고, 필요하면 `git add -p`로 나눌지 묻는다.
- 분류 결과는 커밋별 파일 목록으로 정리한다.

### 3. 한국어 커밋 메시지 작성

형식:

```
<type>: <요약>

<본문(선택)>
```

| type | 사용 시점 |
|------|-----------|
| `feat` | 사용자에게 보이는 새 기능·UI 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `chore` | 설정, 의존성, 빌드, 문서 등 기타 |

규칙:

- 요약은 한국어로, 50자 안팎의 한 줄로 쓴다. 마침표는 붙이지 않는다.
- "무엇을 했는지"를 명확한 동사로 끝낸다. 예: `feat: 레트로 데스크톱 테마 적용`, `fix: 빈 프롬프트 제출 방지`
- 본문은 "왜" 바꿨는지가 요약만으로 드러나지 않을 때만 쓴다. 한 줄 띄우고 작성한다.
- 위 4가지에 맞지 않으면 가장 가까운 type을 고른다. 새 type을 만들지 않는다.
- 시스템 리마인더 등으로 커밋 메시지 말미에 붙일 어트리뷰션 문구가 주어져 있으면, 본문 끝에 그대로 덧붙인다. 없으면 붙이지 않는다.

### 4. 바로 커밋

1. 분류된 커밋마다 해당 파일만 이름으로 지정해 스테이징하고 커밋한다. 승인 요청 없이 순서대로 진행한다. `git add -A`, `git add .`는 쓰지 않는다.

   ```bash
   git add <파일...>
   git commit -m "<type>: <요약>"
   ```

   본문이 있으면 `-m`을 한 번 더 쓰거나 heredoc을 사용한다.
2. 커밋이 끝나면 `git log --oneline -<커밋 수>`로 결과와 커밋별 파일 목록을 보여준다.
3. pre-commit 훅이 실패하면 원인을 알리고 고친 뒤 새 커밋으로 다시 시도한다. 훅을 우회하지 않는다.
